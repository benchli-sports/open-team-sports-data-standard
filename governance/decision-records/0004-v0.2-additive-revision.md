# 0004 - v0.2: an Additive Revision in a New Schema Tree

## Status
Proposed (2026-11-02). Schemas follow once the shape below is agreed.

## Context
v0.1 is in real use: producers export and import v0.1 packages, including a
club's season history, and validate every record against the published schemas.
Valid v0.1 packages exist in the wild.

Mapping what grassroots teams actually record onto v0.1 shows that the standard
forces lossy mappings in a few recurring places:

- **Closed enums are too narrow.**
  - `payment_record.status` has no value for a payment settled outside the
    platform, a waived fee, a partial refund or a dispute, so a producer must
    pick a wrong value, for example `pending` for a fee paid in cash.
  - `game.status` has no `postponed` or `suspended`, so a producer must pick
    another value, for example `scheduled`.
- **Attendance is not the same as intent.** `appearance` records only
  `played`, so "dressed but did not play", "injured" and "scratched" are lost.
- **Things a team really keeps have no home.** These are lineups and batting
  orders, a score per period or inning, an agreed or disputed result between two
  teams, how a game ended (mercy rule, forfeit), the rule set a competition is
  played under, whether a game counts towards records, and players a manager
  keeps on someone's behalf.
- **Money is a float** (`amount`), and a payment cannot point at the request it
  settles: `request_id` names no entity.
- **Nothing says what a metric means.** `stat_line.metrics` keys are
  producer-defined with no catalog, so a consumer cannot tell a pitch count from
  a goal count.
- **Erasure is invisible.** When personal data is erased under a privacy
  request, a package cannot say that a record was removed on purpose rather than
  lost.

Governing bodies are natural adopters. A baseball or softball league, for
example, needs inning line scores, batting orders, a run (mercy) rule,
forfeit scores, pitch-count rules and league-specific rule sets. v0.1 can
express none of these except as opaque extensions.

## Decision

### 1. A new `schemas/v0.2/` tree; v0.1 is frozen
- v0.2 is published as a separate tree. `schemas/v0.1/` is not changed again.
- **Why a new tree for data-additive changes.** `governance/versioning.md` lets
  a minor version take new optional fields in place, and DR-0003 did that. Two
  things in this revision would still break existing readers, even though no
  existing data becomes invalid:
  - widened closed enums: a v0.1 validator rejects the new values;
  - the record envelope and the manifest pin `schema_version` to `"0.1"` with
    `additionalProperties: false`.

  Valid v0.1 packages exist, so they cannot be corrected in place. This record
  states the policy, and a one-line amendment to `governance/versioning.md`
  follows on issue #5: "A change that a strict reader of the current minor would
  reject (a widened enum, a new envelope value) opens a new schema tree, even
  when it adds no required field."
- **Writers emit `"0.2"`. Readers accept `"0.1"` and `"0.2"`** and select the
  schema tree by the package's `schema_version`. One package has one
  `schema_version`: the manifest and every record envelope agree.
- **Compatibility promise.** Any v0.1 record that uses only v0.1-defined fields,
  re-stamped `"0.2"`, is a valid v0.2 record. (A v0.1 record carrying an
  undeclared extra field that v0.2 now defines, for example `event_id` on
  `availability`, is checked against the v0.2 definition.)
- Breaking changes to data wait for v1.0 (section 6).

### 2. Wider enums and the game outcome

**`payment_record.status`**
- Gains `processing`, `paid_offline`, `waived`, `partially_refunded`,
  `disputed` and `charged_back`.
- `paid_offline` and `waived` count as settled for "who still owes".

**`game.status`**
- Gains `postponed` (the game will be replayed at another time) and `suspended`
  (play stopped and may resume).

**`game.outcome`, new optional object: one place for how a game was decided.**
- **Shape:** `{ "method", "awarded_to_team_id", "score_home", "score_away" }`.
- **`method`** is `regulation`, `mercy_rule`, `forfeit`, `abandoned` or
  `other`.
- **Forfeits:** `awarded_to_team_id` and the awarded scores apply. The awarded
  score is the one the rules give (for example 9-0 or 7-0), which may differ
  from any score recorded on the field.
- **`abandoned`:** a game stopped for good with a result declared. A stopped
  game that may resume is `status: suspended`; a game called off with no result
  is `status: cancelled`.
- **v0.1's `status: forfeit`:**
  - It stays valid as a deprecated alias in v0.2, and v1.0 removes it.
  - A v0.2 writer emits `status: completed` with `outcome.method: forfeit`.
  - A reader that meets `status: forfeit` treats it the same way.
  - If both are present, `outcome` wins.

**`availability`**
- `game_id` becomes optional. New optional `event_id` lets availability cover
  trainings and other events, and exactly one of `game_id` / `event_id` is
  required.
- Gains optional `reason` (the shared vocabulary in section 3) and `set_by`:
  `player`, or `manager` for a mark made on the player's behalf.
- `status` stays `yes`, `no`, `maybe` or `unknown`. It is intent only.

### 3. New optional fields on existing entities

**One reason vocabulary** serves both `availability.reason` and
`appearance.reason`: `injured`, `ill`, `away`, `work`, `scratched` (left out by
the coach), `no_show` or `other`.

| Entity | Field | Meaning |
|---|---|---|
| `appearance` | `attendance_status` | `played`, `dressed` (in the squad, did not play) or `absent`. It records what happened, alongside the existing `played` boolean. |
| `appearance` | `reason` | Why a player was absent or did not play, from the shared vocabulary. |
| `game` | `counting_scope` | `official` (default) or `friendly`. A `friendly` game (friendly, scrimmage, exhibition) is excluded from records, standings and career totals. |
| `game` | `segments` | The score per period, inning, end or set: `{ "home": [int], "away": [int] }`. It is in the absolute home/away frame, the same frame as `home_score`/`away_score`, and includes extra segments. `home` may have one entry fewer than `away` when the home side did not need its last half-inning. A game ended early (mercy rule, darkness) records the segments actually played, with the last one partial. |
| `game` | `result` | The reconciliation between two teams: `state` (`reported`, `agreed` or `disputed`), `reported_by_team_id`, `confirmed_by_team_id`, `reported_home_score`, `reported_away_score`, `dispute_reason`. The game's own scores stay the producer's view. |
| `competition` | `rule_set` | `{ "governing_body", "id", "name" }`, for example a national league versus a regional league of one federation. It is declared once per competition and is a name, never the rules themselves. |
| `game` | `rule_set` | It overrides the competition's rule set for one game. |
| `team` | `rule_set` | The rule set a team plays under when no competition record is exported. A producer that stores rule sets per team mirrors them here. |
| `season` | `team_id` | Optional. It makes a season team-scoped; omit it for a season shared by a whole competition. |
| `player` | `managed` | `true` when a team manager holds this record on the person's behalf and the person has no account. A consumer must not assume it can contact them. |
| `venue` | `postal_code`, `address_line`, `indoor`, `venue_type`, `sport`, `aliases` | Fields producers already hold and consumers need to match venues across systems. |
| `team` | `timezone` | Optional IANA zone for the team's local schedule. |
| `payment_record` | `method` | `card`, `cash`, `bank_transfer`, `credit_offset` or `other`. |
| `payment_record` | `amount_minor` | Integer amount in minor units (ISO 4217 exponent). `amount` becomes optional when `amount_minor` is present (a relaxation), and when both are present `amount_minor` wins. |

**Identity across producers (governing-body adopters).** A federation that
receives both clubs' packages holds two one-sided `game` records for one
fixture. They join on `external_ids`:
- The federation's fixture id and each player's licence number travel in
  `external_ids` with `system` set to the governing body's identifier.
- `result` reconciliation and season standings across clubs depend on it.

v0.2 adds no new mechanism for this; it makes it the documented convention.

### 4. New record types
- **`lineup`**: one per game and team. It carries `game_id`, `team_id` and
  `entries[]`. Each entry is `{ player_id, position, line, batting_slot,
  starter }`, all optional except `player_id`.
  - `batting_slot` (1..n) is the batting order. A designated-hitter lineup is
    expressed by a fielder with no `batting_slot`, so a lineup can have more
    starters than batting slots.
  - `line` serves line-based sports (ice hockey, floorball).
  - `lineup` complements `roster_snapshot`, which stays "who was on the roster".
- **`payment_request`**: what was asked for. It carries `team_id`, `purpose`,
  `amount_minor`, `currency`, `due_date`, `status` (`open`, `overdue`, `paid`
  or `cancelled`) and an optional `event_id`.
  - As a new type it carries integer money only.
  - `payment_record.request_id` now references it. A dangling `request_id` is
    reported in the manifest's `missing_references`, never rejected.
- **`stat_definition`**: the catalog entry for a metric key. It carries `key`,
  `sport`, `scope` (`player`, `team` or `line`), `type` (`integer`, `number`,
  `boolean` or `string`), optional `min`/`max`, `label` and `group`.
  - A package SHOULD include a definition for every metric key it emits.
  - Keys the standard names in `spec/05-extensions.md` keep their meaning.
- **`tombstone`**: `{ "entity_type", "id", "removed_at", "reason" }`. `reason`
  is `erasure_request`, `retention` or `producer_deleted`.
  - A tombstone contains no personal data.
  - A package never contains both a tombstone and the record it names.
  - Consumers MUST delete or anonymise their copy of the named record on import.

### 5. Package manifest
- `schema_version` accepts `"0.2"`.
- An optional `redactions` block: per entity type, the count of records withheld
  or tombstoned, and why. A consumer can then tell a deliberately partial export
  from a broken one.

### 6. Out of scope for v0.2
- **Deferred to v0.3 (additive, lower priority):** polls, achievements, and a
  role vocabulary for `membership.roles`.
- **Deferred to v1.0 (breaking):**
  - integer-only money (drop `amount`);
  - numeric-only scores;
  - renaming `competition`;
  - constraining `sport` to the vocabulary;
  - dropping the legacy `otsd_version` alias;
  - removing `status: forfeit`.

  Until v1.0, a sport vocabulary with aliases is published as a
  non-normative list in the spec.

## Consequences

### Positive
- The lossy mappings listed above become round-trips: settled offline payments,
  postponed and suspended games, attendance, lineups and batting orders, line
  scores, agreed results, rule sets, managed players, and erasures.
- A baseball or softball governing body can exchange a season's games without
  extensions, including line scores, batting orders, mercy-rule endings,
  forfeits and the league's rule set. Both clubs' records join on the
  federation's own ids.
- How a game was decided lives in one place (`outcome`), so two producers
  cannot describe the same forfeit differently.
- Metric keys become self-describing, so a consumer can import a sport it has
  never seen.

### Neutral / Migration
- v0.1 readers reject `"0.2"` packages, by design. A producer serving old
  consumers can keep emitting v0.1 until they upgrade. The intended order is:
  1. producers fix any v0.1 mappings that v0.1 can already express;
  2. v0.2 schemas land;
  3. producers adopt v0.2;
  4. connectors re-vendor.

### Risks
- **`tombstone` and `redactions`:** they must never leak what was erased. The
  schemas will forbid every field beyond those listed, and the spec's security
  and privacy chapter gains the rule.
- **`rule_set`:** it names rules without defining them. Two producers can use
  different ids for the same league until the governing body publishes its own.
  `governing_body` narrows that.
- **`team.timezone`:** not every producer holds a team-level zone. It stays
  optional, and consumers fall back to the event's own offset.

## Open questions (to settle before the schemas are written)
1. **`stat_definition` and the extensions chapter.** Should the sport-specific
   keys in `spec/05-extensions.md` move into published `stat_definition`
   records, so the catalog has one source?
2. **A shared reason vocabulary.** Is the single list in section 3 right for
   both availability and attendance, or does each need its own?
